# Архитектура Svoe Vino

## 1. Общая схема

Svoe Vino состоит из трёх логических частей:

```text
┌──────────────────────────────┐
│          Frontend            │
│     svoe-vino-scanner        │
│            Nuxt              │
└──────────────┬───────────────┘
               │
               │ POST /api/scan
               │ multipart/form-data
               │ file=<image>
               ▼
┌──────────────────────────────┐
│      Integration Layer       │
│        integration.py        │
│                              │
│  адаптация API-контрактов    │
└──────────────┬───────────────┘
               │
               │ вызов существующей
               │ backend-логики
               ▼
┌──────────────────────────────┐
│           Backend            │
│       wine_detection         │
│          FastAPI             │
│                              │
│ распознавание + каталог вин  │
└──────────────┬───────────────┘
               │
               ├── сервис распознавания
               │
               └── локальный каталог вин
```

## 2. Принцип разделения

Frontend и backend являются самостоятельными частями приложения.

Интеграционная логика вынесена в `integration.py`. Этот слой существует для согласования интерфейса frontend с существующим API и моделями backend.

Таким образом:

```text
Frontend ≠ Backend ≠ Integration
```

Изменения интерфейса не должны автоматически приводить к изменению backend, а изменения backend — к переписыванию frontend. Несовпадения транспортных контрактов по возможности решаются на интеграционном уровне.

## 3. Frontend

Каталог:

```text
svoe-vino-scanner/
```

Ответственность frontend:

- интерфейс загрузки фотографии;
- отправка изображения;
- отображение состояния обработки;
- обработка ответа интеграционного API;
- навигация на страницу вина;
- отображение карточек и пользовательского интерфейса.

Frontend использует интеграционный endpoint:

```http
POST /api/scan
```

и не обязан знать внутреннюю структуру ответа backend.

## 4. Integration Layer

Файл:

```text
integration.py
```

Это граница между frontend и backend.

Основные задачи слоя:

1. принять HTTP-запрос от frontend;
2. получить загруженный файл;
3. передать его существующей backend-логике;
4. получить результат backend;
5. сопоставить результат с данными, необходимыми frontend;
6. вернуть компактный стабильный контракт.

Пример ответа:

```json
{
  "found": true,
  "wine": {
    "slug": "example-wine-slug"
  }
}
```

За счёт этого frontend зависит от небольшого публичного контракта, а не от полной внутренней модели backend.

## 5. Backend

Каталог:

```text
wine_detection/
```

Backend отвечает за предметную логику приложения:

- анализ изображения;
- распознавание данных с этикетки;
- работу с моделями данных;
- поиск и подбор записей в каталоге;
- формирование результата анализа.

Integration Layer использует backend как источник результата и не должен дублировать его предметную логику.

## 6. Поток данных

Полный E2E-поток:

```text
[Пользователь]
      │
      │ загружает фотографию
      ▼
[Nuxt Frontend]
      │
      │ POST /api/scan
      │ multipart/form-data
      ▼
[integration.py]
      │
      │ передаёт изображение
      ▼
[Backend]
      │
      ├── распознавание изображения
      ├── обработка результата
      └── работа с каталогом
      │
      ▼
[integration.py]
      │
      │ преобразование результата
      │ в frontend-контракт
      ▼
{
  "found": true,
  "wine": {
    "slug": "..."
  }
}
      │
      ▼
[Nuxt Frontend]
      │
      ▼
/wine/<slug>
```

## 7. API-контракт интеграции

### Request

```http
POST /api/scan
Content-Type: multipart/form-data
```

Форма:

```text
file: <image>
```

### Response

Основной контракт для найденной карточки:

```json
{
  "found": true,
  "wine": {
    "slug": "string"
  }
}
```

`slug` является связующим идентификатором для навигации frontend.

## 8. Точка запуска

Файл:

```text
run.py
```

Используется как единая точка входа для объединённого проекта.

Он позволяет запускать проект из корня, не превращая frontend или backend в место хранения интеграционной инфраструктуры.

## 9. Правило развития проекта

При дальнейшей разработке рекомендуется соблюдать границы:

```text
UI / UX / страницы
        → svoe-vino-scanner/

распознавание / каталог / предметная логика
        → wine_detection/

стыковка API / адаптация контрактов
        → integration.py
```

Если для соединения компонентов появляется новая логика, сначала следует определить, является ли она предметной логикой или только адаптацией.

Предметная логика относится к backend. Адаптация форматов и транспортных контрактов относится к интеграционному слою.

## 10. Проверка интеграции

Минимальный smoke test:

```bash
curl -i -X POST http://localhost:8000/api/scan -F "file=@wine.jpg"
```

Для полной E2E-проверки необходимо также загрузить изображение через браузер и убедиться, что запрос проходит через `/api/scan`, возвращает корректный контракт и frontend выполняет переход на `/wine/<slug>`.
